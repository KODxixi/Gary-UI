# Gary-UI 图示表达规范

本规范规定关系型图示怎么承载判断：结构（系统由什么组成）、过程（谁在什么条件下做什么）、状态（现在成立到什么程度）。它不替代数据图表，也不把简单文档流程升级成工程图。

**[spec/diagram-recipes.json](../spec/diagram-recipes.json) 是机器真源。** 本文解释理由、适用前提、可复制的实现与失败条件；色值取 [chart-recipes.json](../spec/chart-recipes.json) 的 `themes`，表面与场景取 [scene-recipes.json](../spec/scene-recipes.json)，引擎能力取[视觉适配器](../adapters/visual/README.md)。本文不复述具体数值。

**参考实现**：[examples/visuals/diagram-spec/reference.html](../examples/visuals/diagram-spec/reference.html)。它是一张符合本规范的真实图；复用时改拓扑与文案，不改规则。

## 0. 与相邻规范的分工

| 读者要什么 | 用什么 | 权威 |
|---|---|---|
| 读数值、比量、看趋势与分布 | 数据图表（ECharts / AntV） | [CHART_EXPRESSION.md](CHART_EXPRESSION.md) |
| 看清对象之间**是否成立**、缺口在哪一侧 | 图示 | 本文 |
| 交代步骤顺序，无分支无边界 | Mermaid 或有序列表 | [capabilities.json](../adapters/visual/capabilities.json) |
| 罗列字段、权限、版本对照 | 表格 | [DESIGN.md](../DESIGN.md) |

图示的成本高在它**必须下判断**。如果关系本身不是结论，画图只会把不确定性放大成形状。

## 1. 三类断言

图先声明它在断言什么，再选形状。三类的失败方式不同：

| 断言 | 适用 purpose | 该回答的问题 | 典型失败 |
|---|---|---|---|
| 结构 | `architecture` | 谁属于哪个分块，主路径经过谁 | 画成组件清单，读者看不出缺口在哪一侧 |
| 过程 | `workflow` / `sequence` / `data-flow` | 谁在什么前提下做了什么，异常在哪断开 | 只画 happy path，异常分支靠文字补 |
| 状态 | `lifecycle` | 对象现在停在哪个状态，回到哪、停在哪 | 状态名当装饰，没有真实转移条件 |

## 2. 七层阅读结构

层次是读图顺序，不代表七层都要画成容器。

| 层 | 负责什么 | 执行要求 |
|---|---|---|
| 断言 | 这张图回答什么判断 | 标题给主题或问题；未验证的结论不写成标题 |
| 主路径 | 读者沿哪条线读 | 恰有一条主路径；分支从主路径节点离开，不并列第二条主干 |
| 分块 | 哪里成立、哪里不成立 | 分块标签是陈述句（「已齐备」「缺口在这里」），不是分类名词 |
| 节点 | 对象是什么 | 节点名写事实身份：模块名、文件名、接口、端口 |
| 关系 | 对象之间是否已成立 | 线型承担成立性；每条虚线都要能说出它为什么不是实线 |
| 证据 | 凭什么这么说 | 标签与细节可回指文件、接口、命令或契约字段；给不出就标未知 |
| 判断 | 读完之后改什么决定 | 结论卡片与图同源，每条可回指图中节点或关系 |

## 3. 五条硬语法

### 3.1 唯一主路径

主路径是读者的默认读序。出现两条并列主干时，读者必须自己选一条，判断权就从图转移到了读者身上。分支一律从主路径节点离开，并在视觉上更短。

### 3.2 分块是状态命题，不是分组框

分块只有在**说出了「这边成立、那边不成立」**时才成立。一个只用来把同类节点圈起来的框会诱导读者以为两侧对等，而真实情况常常是一侧齐备、一侧缺口——这恰好是多数架构评审要看的东西。

分块标签写成命题：「控制面 · 已齐备」「执行体 · 稀疏」。这不是文风问题：读者从标签就该知道该往哪一侧要证据。

### 3.3 分块与卡片是两层

分块是**容器**，卡片是**对象**。两者视觉上必须能分清，否则读者会把「这一块」当成「这个东西」。区分靠强度（见 §4），不靠形状：分块用虚线细边 + 极淡填充，卡片用实线边 + 较浓填充。

一个分块里可以只有一张卡片，也可以有很多张；卡片不能当作分块的标签。

### 3.4 节点只写事实，状态另置

节点名放**能回指的身份**：`ArchOS Core` / `personal-assistant-chat.ts` / `HTTP :7701`。状态放标签位（`已接通` / `未接通` / `仅模型通道` / `拟接入`）。

两者混写会产生一种具体的错：把「已登记」写成「有能力」。这类错在图上无法被读者发现，因为节点名本身就在替它背书。

状态词是闭集，见 §5，不自创新词。

### 3.5 关系：线型管成立性，颜色管归属

| 线型 | 含义 |
|---|---|
| 实线 | 已成立：现有调用、现有数据流 |
| 虚线 | 未成立：规划、外部、待接入、已废弃 |

一条虚线如果说不清「为什么不是实线」，它就该是实线；反过来，把未成立画成实线是本规范最严重的一类错误，因为读者会据此做资源安排。

颜色不参与这个判断：**线色取它指向的节点的分组色**，回答的是「这条线进入哪个分组」，见 §4。

## 4. 分层着色

页面底、分块、卡片、连线、文字是五个独立的层。**只有页面底锁定无彩**，其余三层用同一套分类色、以不同强度表达。

| 层 | 色相 | 强度 | 读作 |
|---|---|---|---|
| 页面底 | 无（chroma = 0，纯 K） | — | 画布 |
| 虚线分块 | 该分块的身份色 | 最弱：边框 46%、填充 5%、标签插值 52% | 容器 / 作用域 |
| 卡片 | 该对象的分组色 | 居中：填充 20%、边框 62% | 对象 |
| 连线 + 箭头 | 目标节点的分组色 | 最实：纯色 | 关系 / 流向 |
| 文字 | 不上色 | — | 内容 |

色值一律取 `spec/chart-recipes.json` 的 `themes.dark.category1..8`，**按职责分组，同类对象同色**（例如两个安全组件同色），不按出现顺序轮转。分块的身份色取该块主对象的族色。

颜色只承担类别，**不得暗示未定义的强弱、成熟度或风险等级**（[CHART_COLOR.md](CHART_COLOR.md)）。用红色表达「这一侧不行」会把两类完全不同的问题压成同一种：实现缺失和实现错误。前者该改计划，后者该改代码。

**缺口与未成立一律由线型（实/虚）与状态词表达**，不交给颜色。

## 5. 状态词汇（闭集）

| 词 | 含义 | 需要证据 |
|---|---|---|
| `已接通` | 有实现 + 输入验证 + 真实成功证据 | 是 |
| `未接通` | 已登记但无可调用能力 | 是 |
| `仅模型通道` | 只能生成文本，不能执行工具 | 否 |
| `拟接入` | 位置与契约已确认，尚未落地 | 否 |
| `未知` | 当前无法判定 | 否 |

`未知` 不得省略。留空会被读成「大概率已成立」，而它通常正是本轮要查的东西。

## 6. 跨边界必须绕行

跨越分块的连接必须显式绕行，不直穿分块边框。

理由不是美学，是背书：把一个尚未纳入分块的组件画在框内，等于宣布它已经受该分块的身份、审批与失败语义约束。绕行的长度本身是证据——读者看到那条长线，就知道这里还差一层接入。

契约未落地的外部运行时尤其如此。它接进来以后线变短，是因为它已经在内，而不是因为版面更整齐。

## 7. 结论卡片与图同源

图下方的卡片是判断层，不是补充说明。每一卡片的每一条，都必须能回指图中的某个节点、某条关系，或节点标签里的事实身份。卡片里出现图中没有的对象，说明图不完整或卡片在推断——两者都要改。

三张卡片的稳定分工：**边界内已经保证了什么 / 缺口在哪一侧 / 落地前必须先验什么**。最后一张最容易写成愿望，它必须写可验证的条件（某接口是否幂等、某字段是否由权威方传入），而不是「注意安全」。

卡片可用左侧色条标分组，色条与图中对应分块同族；色条不表达好坏。

## 8. 失败条件

出现任一条即不算合格图示：

- 分块只当分组框，读者读不出「已具备 / 缺口」
- 分块与卡片用同一强度，读者分不清容器与对象
- 用颜色表达成败、成熟度或风险
- 状态词写进节点名，与事实身份混写
- 用了虚线但线型含义未声明，或同图虚线含义不一致
- 关系标签无法回指文件、接口、命令或契约字段
- 结论卡片出现图中没有的节点或关系
- 主路径分叉成多条并列主干
- 已登记但未接通的能力被画成已具备
- 外部运行时被画在它尚未纳入的分块之内

## 9. 场景与交付

场景决定预设，不由图型随意分配（[theme-map.json](../adapters/visual/theme-map.json)）：

| scene | archify preset | 适用 |
|---|---|---|
| `reading` | `classic` | 正文内的解释图，读者按顺序读 |
| `analysis` | `signal-flow` | 评审与诊断，需要指出缺口与判断 |
| `showcase` | `blueprint` | 展示与汇报，动效有明确结束状态 |

交付走固定顺序，不跳步：**manifest validate → adapter render → export → 浏览器无溢出**。原生 JSON 源与清单一起保留，产物在 `outputRoot` 内生成。

任一环节未 pass 仍可作草稿，但不得称为定稿或已交付。

## 10. 引擎边界（当前已知缺口）

`archify` 的 `visual_preset` 自带一整套语义色板（前端青 / 后端绿 / 数据库紫 / 安全玫红 / 消息总线橙 / 蓝强调），**它不读 Gary token**，`theme-map.json` 对 archify 只生效 `fontFamily`。它的节点色与深蓝底是配套的，单取节点色会破坏对比关系。

因此：**纯 K 作用域（企业面板、ArchOS 工作台）的图示按本规范手写 SVG**，用附录 A 的分层实现。需要 archify 的可交互产物时，先确认该图不属于该作用域；否则等引擎支持 palette 覆盖后再派发，**不做后处理换色**（会破坏交付回执的确定性）。

`theme-map.json` 的 `dark` 主题已按企业面板 v1.2 收敛（`#141414` / `#1c1c1c` / `#cfd0d3`）；`light` 仍是旧值，等浅色面板 token 定稿后统一。

## 11. 用完整场景验证

图示语法是否正确，只能在真实判断上检验：换成另一套业务结论后，同一张图是否仍然成立。若一张图只能解释它被画出来的那个结论，它就不是语法，是一次配图。

## 附录 A：最小实现

五层的可复制实现（Chrome 111+，依赖 `color-mix()` 与 `context-stroke`）。分类色由使用处通过自定义属性注入，样式不硬编码任何 category 值。

```css
:root{
  /* 页面底：纯 K，chroma = 0 */
  --k-page:#141414; --k-card:#1c1c1c; --k-raised:#262626; --k-line:#333333;
  --t-strong:#f7f7f7; --t-body:#c3c4c7; --t-meta:#9d9ea2; --t-faint:#7c7d81;
}
body{background:var(--k-page);color:var(--t-body)}

/* 分块：最弱 —— 容器 */
.bnd{fill:color-mix(in srgb,var(--b) 5%,transparent);
     stroke:color-mix(in srgb,var(--b) 46%,transparent);
     stroke-width:1;stroke-dasharray:6 5}
.bnd-t{fill:color-mix(in srgb,var(--b) 52%,var(--t-strong));font-size:11.5px;font-weight:500}

/* 卡片：居中 —— 对象 */
.node{fill:color-mix(in srgb,var(--c) 20%,var(--k-card));
      stroke:color-mix(in srgb,var(--c) 62%,#2e2e2e);stroke-width:1}
.node-open{fill:color-mix(in srgb,var(--c) 7%,var(--k-page));
           stroke:color-mix(in srgb,var(--c) 45%,transparent);stroke-dasharray:5 4}

/* 连线：最实 —— 关系 */
.edge{fill:none;stroke:var(--e);stroke-width:1.8}
.edge-open{fill:none;stroke:var(--e);stroke-width:1.35;stroke-dasharray:5 4}
marker path{fill:context-stroke}   /* 箭头跟随线的颜色 */

/* 文字：不上色 */
.ntitle{fill:var(--t-strong);font-size:13px;font-weight:600}
.nsub{fill:var(--t-meta);font-size:10px}
.elabel{fill:var(--t-meta);font-size:10.5px;
        paint-order:stroke;stroke:var(--k-page);stroke-width:4.5px}
```

用法：分块写 `style="--b:#d5af59"`，卡片组写 `style="--c:#78c9ac"`，连线写 `style="--e:#82acec"`（取其目标节点的分组色）。箭头统一引用同一个 `context-stroke` marker，不要为每种颜色复制一份。

## 附录 B：参考实现

[examples/visuals/diagram-spec/reference.html](../examples/visuals/diagram-spec/reference.html) 是一张完整实例：两个分块（一个已齐备、一个稀疏）、四个现状不同的执行器、一条绕出分块的逃逸线、三张与图同源的结论卡片。

复用它时改**拓扑、文案与分组色**，不要改分层强度、状态词闭集与绕行规则——那三条是本规范本身。
